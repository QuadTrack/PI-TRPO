
Задание 1. Анализ архитектуры и рефакторинг
1. Нарушенные принципы проектирования

Класс UserManager представляет собой классический пример антипаттерна God Object (Всезнающий объект). В нем нарушены ключевые принципы SOLID и GRASP:

    Single Responsibility Principle (SRP): Класс имеет сразу 6 различных причин для изменения (работа с БД, бизнес-логика авторизации, логика уведомлений, генерация отчетов, аутентификация, логирование).

    Open/Closed Principle (OCP): Любое изменение в формате отчетов, способе логирования или типе базы данных потребует прямого редактирования кода UserManager.

    High Cohesion (GRASP): Класс обладает низким связыванием внутри себя, так как объединяет совершенно разнородную функциональность.

    Separation of Concerns (SoC): Смешаны слой хранения данных (Persistence), бизнес-логика (Domain logic) и инфраструктурные сервисы (Notification/Logging).

2. Перепроектирование системы

Систему необходимо разделить на специализированные сервисы и сущности:

[User] (Domain Entity) ──> [UserRepository] (Data Access)
                             │
[AuthService] ───────────────┼──> [UserManager / UserService] (Business Logic)
                             │           │
[NotificationService] ───────┼───────────┤
[ReportGenerator] ───────────┼───────────┘
[LoggerService] ─────────────┘ (Cross-cutting concern)

[User] (Сущность данных)
   ▲
   │
[UserRepository] ─── (Работа с базой данных)
   ▲
   │
[UserManager / UserService] ─── (Центральная бизнес-логика)
   │
   ├───> [AuthService] ────────── (Проверка прав и авторизация)
   ├───> [NotificationService] ── (Отправка email и сообщений)
   ├───> [ReportGenerator] ────── (Формирование отчетов)
   └───> [LoggerService] ──────── (Запись логов и событий)

    User (Entity): Данные пользователя и методы их валидации.

    UserRepository / IUserRepository (Data Access Layer): Изолирует работу с базой данных (CRUD-операции).

    UserService (Domain Layer): Основная бизнес-логика управления пользователями.

    AuthService / AccessControlService: Управление правами доступа, ролями и авторизацией.

    NotificationService / IEmailService: Отправка email и других уведомлений.

    ReportGenerator: Формирование отчетов на основе данных.

    Logger (Infrastructure): Сквозное логирование (Cross-cutting concern), внедряемое через DI (Dependency Injection) или АОП (аспектно-ориентированное программирование).

Задание 3. Архитектурный стиль для системы "Библиотека"
Выбор: Модульный монолит (Modular Monolith)

Для заданных условий идеальным выбором является модульный монолит (или трехслойная архитектура с четким разделением на слои и модули).
Обоснование выбора:

    Небольшая команда (3–5 человек): В маленькой команде микросервисная инфраструктура создаст огромные накладные расходы (DevOps, распределенная трассировка, межсервисная сеть). Монолит позволит команде сфокусироваться на бизнес-фичах.

    Ограниченный бюджет: Запуск одного приложения на базовом сервере/VPC стоит значительно дешевле, чем поддержка кластера для микросервисов.

    Нагрузка 1000 пользователей: Это незначительная нагрузка. Один монолитный экземпляр легко обрабатывает десятки тысяч активных пользователей.

    Расширяемость без переписывания кода: Модульная архитектура (DDD / Hexagonal / Clean Architecture) позволяет четко разделить контексты (Каталог, Выдача книг, Пользователи). Добавление новых функций происходит путем создания нового модуля, не затрагивающего остальные.

Задание 4. Архитектурное решение для Банковской системы
1. Выбор архитектуры: Микросервисная архитектура (Event-Driven Microservices)

Почему не монолит:

    Размер команды (50 человек): В монолите 50 разработчиков неизбежно будут мешать друг другу в одном репозитории, сталкиваться с конфликтами при слиянии кода и блокировать релизы. Микросервисы позволят разбить команду на 6–8 независимых двупиццевых команд (Two-Pizza Teams).

    Масштабируемость: Нагрузка на транзакционный модуль будет значительно выше, чем на модуль личных настроек или отчетов. Микросервисы позволяют точечно (горизонтально) масштабировать самые нагруженные компоненты.

    Отказоустойчивость: Падение модуля генерации справок не должно приводить к остановке процессинга платежей.

2. Ключевые нефункциональные требования (NFR)

    Performance & Throughput (Производительность): Высокий TPS (транзакций в секунду) и минимальный Latency (задержка response time).

    Availability & Resilience (Доступность): Требование 24/7 (SLA 99.999%, не более 5 минут простоя в год).

    Scalability (Масштабируемость): Способность справляться с пиковыми нагрузками (миллионы операций).

    Security & Compliance (Безопасность): Соответствие стандартам PCI-DSS, шифрование данных, аудит действий.

    Data Consistency (Согласованность данных): Строгие требования к ACID в транзакциях и итоговой согласованности (Eventual Consistency) в распределенных сценариях.

3. Обеспечение безопасности и надёжности

Безопасность:

    Аутентификация/Авторизация: OAuth2 / OpenID Connect + JWT с коротким временем жизни. API Gateway как единая точка входа и проверки токенов.

    Защита данных: Шифрование данных в покое (Data at Rest — AES-256) и в движении (Data in Transit — mTLS между сервисами).

    Zero Trust Security: Каждый микросервис проверяет права запроса, внутрисетевой трафик изолирован.

    Аудит: Неизменяемый журнал всех транзакций (Audit Trail / Event Sourcing).

Надёжность и отказоустойчивость:

    Паттерны устойчивости: Использование Circuit Breaker (предохранитель), Rate Limiting (ограничение частоты), Retry с экспоненциальной задержкой.

    Развертывание без простоя: Стратегии Blue-Green deployment или Canary deployment, работы в Kubernetes кластере (Multi-AZ / Multi-Region).

    Асинхронный процессинг: Использование брокеров сообщений (Apache Kafka / RabbitMQ) для сглаживания пиковых нагрузок и предотвращения потери событий.

    Резервирование: Репликация баз данных (Master-Replica / Multi-Master) и автоматическое переключение при сбоях (Failover).
